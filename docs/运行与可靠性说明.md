# 运行与可靠性说明

## 环境与启动方式

应用代码要求 Python 3.12/3.13，当前使用 Python 3.12。数据库使用 PostgreSQL；SQLite 只支持明确标记的轻量检查，无法验证真实行锁，也不支持本项目活动范围查询使用的 JSON contains 操作。

推荐通过 Docker Desktop 的 Linux 引擎运行 PostgreSQL、Redis、Web 和 Worker。默认 `compose.yaml` 只将 Nginx 的 8080 端口映射到 `127.0.0.1`，不会公开监听所有网卡。

完整启动步骤见 [README](../README.md)。先启动数据库，再运行迁移，再启动应用；没有将迁移放到每个 Web 进程的启动钩子里，以避免扩容时多个实例同时迁移。

## 本机 Python 开发

需要热更新 Python 代码时，可只用容器提供数据库和 Redis：

```powershell
Set-Location F:\Website\mainbody
docker compose -f compose.yaml -f compose.dev.yaml up -d db redis
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py createsuperuser
.\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000
```

该覆盖文件只把 5432 和 6379 映射到本机回环地址。`runserver` 只用于开发；Gunicorn 和正式 Celery Worker 使用 Linux 容器。此模式没有自动运行后台进程，调度和 Worker 仍需通过 Compose 单独启动。

默认 PostgreSQL 账号由容器初始化，是本地开发用途；正式环境应拆分数据库管理/迁移账号与权限更小的运行账号，并单独建立测试数据库。

## 已设置的保护

| 位置 | 当前参数或实现 | 用途 |
|---|---|---|
| Django / Nginx | 业务请求体最大 1MiB | 避免大文件占满 Web 内存 |
| Django | 草稿 JSON 最大 32KiB | 限制业务记录大小 |
| 文件元数据 | 单文件最多 10GB，默认分片 32MiB | 限定文件范围；分片传输尚待接入 |
| 上传服务 | 每个账号最多 2 个活跃任务 | 限制并发预留；跨活动统计 |
| PostgreSQL | 连接超时 3 秒、锁等待 3 秒、SQL 10 秒、空闲事务 15 秒 | 减少请求长期占用连接 |
| Gunicorn | 2 进程 × 2 线程、请求超时 30 秒 | 保守起点，后续按压测调整 |
| Gunicorn | 每进程约 500 次请求后错峰回收 | 限制长期进程膨胀影响 |
| Celery | 预取 1，软超时 240 秒、硬超时 300 秒 | 防止单任务长期占用工作进程 |
| Celery | 子进程任务数与内存回收阈值 | 控制长期运行资源占用 |
| Outbox | 30 秒发送租约、900 秒重投、最多 8 次 | 故障恢复及有限重试 |
| Redis | AOF、noeviction、内存上限 | 避免静默逐出排队消息；满载时允许发布失败后重试 |
| Compose | 服务内存/CPU/进程数限制，日志滚动 | 避免一个进程耗尽所有资源 |

检查 Worker 和导出 Worker 分开运行；`maintenance` 当前与检查队列共用 Worker，主要承载探测任务。大量维护任务需要另开 Worker，不能依赖共享队列具有独立资源保证。

容器限制是初始配置，并不表示在任意 2 核/4GB 主机上已验证可用。数据库连接数、所有 Worker、扫描临时磁盘和系统自身资源需要一起计算。单台机器和单实例 PostgreSQL/Redis 仍存在单点故障。

## 任务可靠性机制

业务代码先在 PostgreSQL 事务中写入 `OutboxEvent`。调度器领取待发记录，提交短事务后才访问 Redis，因此网络等待不会长时间占着领取锁。多个调度器可通过 `skip_locked` 避免争抢同一条记录。

发布成功不等于处理成功。记录仍保持 pending；消费者完成并提交数据库后才为 done。若收到重复消息，完成状态和行锁阻止重复写入。若队列故障、发送后进程崩溃或消息丢失，持久记录允许再次投递。

发布失败按退避延后，已发布但未完成的事件在重投时间到达后再次尝试，达到上限后标为 failed。当前没有外部告警系统；需要通过日志/任务后台发现失败和积压，正式环境应补告警。

```powershell
# 生成一个不含学生数据的测试任务，返回任务 UUID。
docker compose exec web python manage.py enqueue_probe

# 观察应用、调度器和消费者日志。
docker compose logs --tail 100 web dispatcher worker-validation

# 排查并修复故障后，显式重试一条失败任务。
docker compose exec web python manage.py retry_job <任务UUID>
```

重试命令只接受 failed 任务。没有实现的检查/导出处理器会失败为 `handler_not_implemented`，仅重复投递不会让该功能自动完成。

## 健康检查与监控范围

`/health/live/` 仅检查进程响应。`/health/ready/` 额外检查 PostgreSQL 与 Redis，不检查对象存储、不检查完整业务链，也不检查 Worker 的工作效率。

Docker 当前使用 live 进行健康检查。Docker 的 restart 策略会在进程退出时重启，但不会仅因为容器标记 unhealthy 自动重启；正式部署应选择明确的编排或监督方式。

请求日志包含路由、状态、耗时和请求编号，不记录正文、原始查询字符串、Cookie 或激活码。审计表与请求日志分开；目前草稿写入已接审计，未来下载、审批和权限更改还需在对应服务中接入。

正式环境需要另行接入任务积压、最老待处理时间、数据库容量、对象存储配额、费用和备份结果告警。

## 生产配置边界

当前 Nginx 文件是本地 HTTP 配置。切换 production 前，需要设置真实域名、HTTPS 证书、HTTPS 监听、可信 CSRF 来源与独立生产密钥。生产设置会拒绝占位密钥、通配主机和非 HTTPS CSRF 来源。

反向代理必须重写 `X-Forwarded-Proto`，且 Web 进程不可直接暴露公网。如果 TLS 在另一层终止，需要按实际网络边界配置，不能直接套用本地 `$scheme=http` 配置，否则会发生 HTTPS 重定向问题。

示例 Nginx 限速按 IP 进行。校园网多人可能共享公网 IP，应在试运行时调整，并补充按账号和操作的登录防暴力机制。当前未实现 MFA、学生激活、密码找回及学校认证。

## 备份与恢复

Compose 已为 PostgreSQL 和 Redis 配置持久卷；持久卷不是备份。当前没有生成自动备份任务，也没有做恢复演练。

正式启用前需要建立：数据库逻辑/物理备份与保留策略、对象存储防误删和备份策略、独立环境恢复验证、备份告警和维护人。恢复必须核对数据库中的对象键是否能对应到正确文件。

日常停止使用 `docker compose stop` 或保留卷的 `docker compose down`。带 `-v` 的删除卷操作会删除本地数据库和消息数据，不用于普通重启。

## 验证方式与证据范围

轻量检查：

```powershell
$env:TEST_SQLITE = '1'
.\.venv\Scripts\python.exe manage.py check --settings=config.settings.test
.\.venv\Scripts\python.exe -m pytest -q
Remove-Item Env:TEST_SQLITE
```

真实 PostgreSQL 检查（使用隔离的测试数据库账号，不对生产库运行）：

```powershell
docker compose -f compose.yaml -f compose.dev.yaml up -d db redis
Remove-Item Env:TEST_SQLITE -ErrorAction SilentlyContinue
.\.venv\Scripts\python.exe -m pytest -q
```

pytest-django 会建立测试数据库，账号需要相应建库权限。单独运行并发检查可加 `-m postgresql`。这些测试用大字节数记录模拟额度，不会生成或上传 10GB 的真实文件。

此外还需进行真实直传与续传验证、队列断连恢复演练、数据库备份恢复以及约定人数的负载测试。当前未完成上述运行验证；最新检查结果见 [验证记录](架构完整性与验证记录.md)。
