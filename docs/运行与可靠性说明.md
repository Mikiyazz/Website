# 运行与可靠性说明

## 环境与启动方式

应用代码要求 Python 3.12/3.13，当前使用 Python 3.12。数据库使用 PostgreSQL；SQLite 只支持明确标记的轻量检查，无法验证真实行锁，也不支持本项目活动范围查询使用的 JSON contains 操作。

推荐通过 Docker Desktop 的 Linux 引擎运行 PostgreSQL、Redis、Web 和 Worker。默认 `compose.yaml` 只将 Nginx 的 8080 端口映射到 `127.0.0.1`，不会公开监听所有网卡。

完整启动步骤见 [README](../README.md)。先启动数据库，再运行迁移，再启动应用；没有将迁移放到每个 Web 进程的启动钩子里，以避免扩容时多个实例同时迁移。

## 本机 Python 开发

需要热更新 Python 代码时，可只用容器提供数据库和 Redis：

```powershell
Set-Location F:\Website\mainbody
docker compose -f compose.yaml -f compose.dev.yaml up -d db redis
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py createsuperuser
.\.venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000
```

该覆盖文件只把 5432 和 6379 映射到本机回环地址。`runserver` 只用于开发；Gunicorn 和正式 Celery Worker 使用 Linux 容器。此模式没有自动运行后台进程，调度和 Worker 仍需通过 Compose 单独启动。

默认 PostgreSQL 账号由容器初始化，是本地开发用途；正式环境应拆分数据库管理/迁移账号与权限更小的运行账号，并单独建立测试数据库。

## 已设置的保护

| 位置 | 当前参数或实现 | 用途 |
|---|---|---|
| Django / Nginx | 业务请求体最大 2100MiB，表单内存阈值 2.5MiB | 大文件流式落临时盘，避免占满 Web 内存 |
| Django | 草稿 JSON 最大 32KiB | 限制业务记录大小 |
| 文件元数据 | 单文件最多 10GB，浏览器分片 5MiB（>10MB 统一分片） | 支持断点续传，防止大上传占死连接 |
| 磁盘剩余空间守卫 | `UPLOAD_MIN_FREE_DISK_BYTES=5GiB`（低于阈值返回 503） | 上传与导出写盘前熔断并打 `disk_space_low` 告警，绝不写爆系统盘 |
| 上传服务 | 每个账号最多 2 个活跃任务 | 限制并发预留；跨活动统计 |
| PostgreSQL | 连接超时 3 秒、锁等待 3 秒、SQL 10 秒、空闲事务 15 秒；`max_connections=120, shared_buffers=256MB` | 支撑 2000+ 师生高并发同时防止慢事务堆积 |
| Gunicorn | 4 进程 × 4 线程（16 槽位）、`preload_app=True`、超时 600 秒 | 面向 4C8G+ 矿大服务器基线，写时复制共享内存 |
| Gunicorn | 每进程约 500 次请求后错峰回收 | 限制长期进程膨胀影响 |
| Nginx | `X-Accel-Redirect`（`/internal-media/` 只读挂载 `media_data`） | 生产模式下把视频/ZIP/导出大包下载完全卸载离 Gunicorn |
| Nginx 校内限流 | 登录 `60r/m burst=200`、全站 `150r/s burst=400` + `set_real_ip_from` | 适配宿舍楼/校内 NAT 共享出口与前置反代，同 IP 百人登录 0 误杀 |
| Celery | 预取 1，常规任务软/硬超时 240/300 秒，异步导出 3600/3660 秒 | 防止单任务长期占用工作进程且允许大活动完整打包 |
| Celery | 子进程任务数与内存回收阈值 | 控制长期运行资源占用 |
| Outbox | 30 秒发送租约、900 秒重投、最多 8 次 | 故障恢复及有限重试 |
| Redis（双实例拆分） | `redis`（Broker：512MB AOF `noeviction`）+ `redis-cache`（Cache：512MB `allkeys-lru` + 默认 300s TTL） | 缓存与任务队列彻底隔离，缓存写满绝不连坐队列派发 |
| 导出防堵/防爆盘 | 异步导出按操作者+活动+模式防连点复用、失败清半成品 `.part`/`.zip`、72 小时自动回收 | 连点不建重复任务、失败不残留大文件、历史包定时清盘 |
| Compose | 服务内存/CPU/进程数限制（`web` 2g/2c、`db` 1536m、`pids_limit: 256`），日志滚动 | 避免单个进程耗尽整机资源 |

检查 Worker 和导出 Worker 分开运行；`maintenance` 当前与检查队列共用 Worker，主要承载探测任务。大量维护任务需要另开 Worker，不能依赖共享队列具有独立资源保证。

容器限制是初始配置，并不表示在任意 2 核/4GB 主机上已验证可用。数据库连接数、所有 Worker、扫描临时磁盘和系统自身资源需要一起计算。单台机器和单实例 PostgreSQL/Redis 仍存在单点故障。

## 任务可靠性机制

业务代码先在 PostgreSQL 事务中写入 `OutboxEvent`。调度器领取待发记录，提交短事务后才访问 Redis，因此网络等待不会长时间占着领取锁。多个调度器可通过 `skip_locked` 避免争抢同一条记录。

发布成功不等于处理成功。记录仍保持 pending；消费者完成并提交数据库后才为 done。若收到重复消息，完成状态和行锁阻止重复写入。若队列故障、发送后进程崩溃或消息丢失，持久记录允许再次投递。

发布失败按退避延后，已发布但未完成的事件在重投时间到达后再次尝试，达到上限后标为 failed。当前没有外部告警系统；需要通过日志/任务后台发现失败和积压，正式环境应补告警。

```powershell
# 生成一个不含学生数据的测试任务，返回任务 UUID。
docker compose exec web python manage.py enqueue_probe

# 观察应用、调度器和消费者日志。
docker compose logs --tail 100 web dispatcher worker-validation

# 排查并修复故障后，显式重试一条失败任务。
docker compose exec web python manage.py retry_job <任务UUID>
```

重试命令只接受 failed 任务。没有实现的检查/导出处理器会失败为 `handler_not_implemented`，仅重复投递不会让该功能自动完成。

## 磁盘与额度回收

分片上传把一次 300MB 拆成 60 个 5MB 请求，代价是任务必须能收尾：学生关掉页面之后，再没有任何请求会碰它。
`UploadSession.expires_at`（分片任务 3 天）过期后由回收任务处理：

```powershell
# 先预演：只统计会清什么，不改数据库也不删文件。
docker compose exec web python manage.py purge_stale_uploads --dry-run

# 真正回收：删 media/tmp/<upload_id>/、扣回 reserved_bytes、状态置 aborted、写 upload.purged 审计。
docker compose exec web python manage.py purge_stale_uploads --limit 500

# 给慢网络同学留余地：过期后再宽限 24 小时才清。
docker compose exec web python manage.py purge_stale_uploads --grace-hours 24

# 接监控时用机器可读输出。
docker compose exec web python manage.py purge_stale_uploads --json
```

`dispatch_outbox` 常驻进程启动时先扫一次，之后每 `--purge-interval` 秒（默认 3600）同步执行**过期分片回收**与**超过 72 小时历史导出包清理**；`--no-purge` 或 `--purge-interval 0` 关闭。回收是幂等的，已 `aborted` 的会话与已清理 `file_path` 的导出记录不会重复处理；单条失败只记录不中断整批，命令在有失败时以非零退出码结束。

历史导出归档包（`MEDIA_ROOT/exports/`）默认保留 **72 小时**（可通过 `EXPORT_RETENTION_HOURS` 调整），也可人工按需触发回收：

```powershell
# 预演检查过期导出包与孤儿半成品
docker compose exec web python manage.py purge_expired_exports --dry-run

# 正式清理超过 72 小时的历史导出包（支持 --hours 覆盖时长、--json 机器输出）
docker compose exec web python manage.py purge_expired_exports --hours 72
```

### 单生默认配额核定建议

模型默认 `Activity.quota_bytes_per_student` 为 **12 GiB**（适配单生最多 5 个 2000MB `.zip` 打包件 + 约 2.4GB 其他材料）。面向 2000+ 人规模，上线新建活动时请结合矿大服务器数据盘实际容量在管理后台按活动核定：

| 数据盘可用容量（建议独立数据盘） | 2000 人场景建议单生配额 | 备注 |
|---|---:|---|
| 500 GB – 1 TB | 1 GiB – 2 GiB | 常规文档+照片+单支宣讲视频绰绰有余 |
| 2 TB | 4 GiB – 6 GiB | 可容纳常规大附件与 1–2 个打包件 |
| 4 TB 及以上 | 12 GiB（默认上限） | 全开 5×2000MB 打包件，同时仍受 5 GiB 剩余磁盘硬保护兜底 |

唯一剩下的残留是"孤儿文件"：事务提交后进程被强杀，文件还在但记录已是 aborted。核对办法是拿 `--dry-run` 输出的 upload_id 对照 `media/tmp/`，或直接给 `media/tmp` 配一条按修改时间的清理策略兜底。

容器部署里 `/app/media` 是命名卷 `media_data`，由 web、dispatcher 和两个 worker 共同挂载。这是回收能生效的前提：只给 web 挂卷的话，dispatcher 里的回收只能改数据库状态、删不掉另一个容器里的字节，等于每次都制造孤儿文件。镜像里已把 `/app/media` 的所有者设为 `app`（uid 10001），卷初始化后才有写权限。

## 健康检查与监控范围

`/health/live/` 仅检查进程响应。`/health/ready/` 额外检查 PostgreSQL 与 Redis，不检查对象存储、不检查完整业务链，也不检查 Worker 的工作效率。

Docker 当前使用 live 进行健康检查。Docker 的 restart 策略会在进程退出时重启，但不会仅因为容器标记 unhealthy 自动重启；正式部署应选择明确的编排或监督方式。

请求日志包含路由、状态、耗时和请求编号，不记录正文、原始查询字符串、Cookie 或激活码。审计表与请求日志分开；目前草稿写入已接审计，未来下载、审批和权限更改还需在对应服务中接入。

正式环境需要另行接入任务积压、最老待处理时间、数据库容量、对象存储配额、费用和备份结果告警。

## 生产配置边界与矿大服务器接入模式

推荐服务器基线：**4 核 8 GB 内存起步**，并挂载独立大容量数据盘（如 `/data/practice-platform`）。

`config/settings/production.py` 与 `deploy/nginx*.conf` 已对齐三种校内接入方式，避免 `SECURE_SSL_REDIRECT` 与代理协议头不一致导致的无限 301 循环：

| 接入模式 | `.env` 关键配置 | Nginx 模板 (`NGINX_CONF_FILE`) | 行为说明 |
|---|---|---|---|
| ① 矿大校内纯 HTTP 内网（无证书） | `DJANGO_USE_HTTPS=false`<br>`DJANGO_CSRF_TRUSTED_ORIGINS=http://<服务器IP或域名>` | `./deploy/nginx.conf`（默认） | 监听 80，首页/登录页直接 200，无 301 死循环 |
| ② 独立 HTTPS 证书 | `DJANGO_USE_HTTPS=true`<br>`DJANGO_CSRF_TRUSTED_ORIGINS=https://<域名>` | `./deploy/nginx.https.conf` | 80 自动 301 跳 443，443 终结 TLS 并传递 `X-Forwarded-Proto: https`，开启安全 Cookie 与 HSTS |
| ③ 学校前置 HTTPS 网关/反代 | `DJANGO_USE_HTTPS=true`<br>`DJANGO_CSRF_TRUSTED_ORIGINS=https://<校内域名>` | `./deploy/nginx.gateway.conf` | 本机监听 80，自动信任内网反代 `X-Forwarded-For` 与 `X-Forwarded-Proto`（缺失回退 `https`） |

所有模板均已开启 `location /internal-media/ { internal; alias /app/media/; }`，生产模式默认 `NGINX_ACCEL_REDIRECT_ENABLED=true`，文件预览/下载与导出包下载经 Django 鉴权后立即交由 Nginx 异步发送，绝不阻塞 Gunicorn 16 槽位。Nginx 限流已放宽至登录 `60r/m burst=200`、接口 `150r/s burst=400`，确保宿舍楼/校内 NAT 共享出口下同 IP 百人集中登录零误杀。

## 大容量数据盘挂载与每日定时备份

Compose 默认使用命名卷方便本机开发；**矿大正式服务器必须使用 `compose.prod.yaml` 将 `postgres_data`、`media_data`、`redis_data` 绑定至宿主机大容量数据盘**，物理级防止系统盘爆满或容器重建丢数据：

```bash
# 1. 宿主机数据盘目录初始化（uid 10001 为镜像内 app 用户）
sudo mkdir -p /data/practice-platform/{postgres,media,redis,certs,backups}
sudo chown -R 10001:10001 /data/practice-platform/media

# 2. 使用生产覆盖配置执行迁移并启动全栈
cd /opt/practice-platform/mainbody
docker compose -f compose.yaml -f compose.prod.yaml --profile setup run --rm migrate
docker compose -f compose.yaml -f compose.prod.yaml up -d
```

### 每日定时备份与恢复演练

仓库已内置每日备份脚本 `mainbody/deploy/backup_daily.sh`，执行三项动作：
1. 核查备份分区剩余空间（低于 10 GiB 告警中止）；
2. `pg_dump -Fc` 热备 PostgreSQL 并用 `pg_restore --list` 校验归档完整性；
3. 使用 `rsync -a --link-dest` 对学生材料目录 `/data/practice-platform/media` 做每日硬链接增量快照（自动排除 `tmp/` 与 `exports/`），默认滚动保留 14 天。

在宿主机 `crontab -e` 中加入每日凌晨 03:00 自动执行：

```cron
0 3 * * * /opt/practice-platform/mainbody/deploy/backup_daily.sh >> /var/log/practice-backup.log 2>&1
```

恢复演练命令示例（在测试库/新机上验证）：

```bash
# 1. 恢复 PostgreSQL（先创建空库或清空测试库）
docker compose -f compose.yaml -f compose.prod.yaml exec -T db \
  pg_restore -U practice -d practice --clean --if-exists < /data/practice-platform/backups/postgres/practice_YYYYMMDD_HHMMSS.dump

# 2. 恢复学生材料目录
rsync -a /data/practice-platform/backups/media/latest/ /data/practice-platform/media/
sudo chown -R 10001:10001 /data/practice-platform/media
```

日常停止请使用 `docker compose stop` 或不带 `-v` 的 `docker compose down`，严禁在生产环境执行 `docker compose down -v`。

```powershell
$env:TEST_SQLITE = '1'
.\.venv\Scripts\python.exe manage.py check --settings=config.settings.test
.\.venv\Scripts\python.exe -m pytest -q
Remove-Item Env:TEST_SQLITE
```

真实 PostgreSQL 检查（使用隔离的测试数据库账号，不对生产库运行）：

```powershell
docker compose -f compose.yaml -f compose.dev.yaml up -d db redis
Remove-Item Env:TEST_SQLITE -ErrorAction SilentlyContinue
.\.venv\Scripts\python.exe -m pytest -q
```

pytest-django 会建立测试数据库，账号需要相应建库权限。单独运行 4 项 PostgreSQL 行锁并发检查可加 `-m postgresql`：

```powershell
docker compose -f compose.yaml -f compose.dev.yaml up -d db redis
$env:TEST_SQLITE = '0'
.\.venv\Scripts\python.exe -m pytest -m postgresql -v
```
