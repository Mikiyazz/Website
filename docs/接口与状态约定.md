## 请求与响应示例

创建草稿：

```http
POST /api/v1/submissions/
Content-Type: application/json
X-CSRFToken: <从本网站获取的令牌>
Cookie: sessionid=<登录会话>

{"activity_id": "<真实活动 UUID>"}
```

成功返回的主体包含 `id`、`activity_id`、`status`、`version`、`draft_data`。首次创建和返回已有草稿均为 HTTP 200，不会重复创建记录。

保存草稿：

```json
{
  "expected_version": 0,
  "draft_data": {"title": "待填写的实践申请"}
}
```

`expected_version` 是上次读取的整数版本号。保存成功后版本加 1；如果另一个页面已经保存，返回 409，应重新读取并提示用户处理冲突。草稿 JSON 当前限制为 32KiB，只作为可编辑字段容器，不应包含文件字节、密钥或权限参数。

错误响应：

```json
{
  "error": {
    "code": "conflict",
    "message": "草稿已被其他页面更新，请重新获取后再保存。"
  },
  "request_id": "请求追踪编号"
}
```

| HTTP 状态 | 场景 |
|---|---|
| 400 | JSON、字段或文件元数据不合法 |
| 401 | 未登录或账号失效 |
| 403 | 角色不允许；CSRF 中间件拒绝也会返回 403 |
| 404 | 对象不存在或不属于当前用户 |
| 405 | 请求方法不支持，附 `Allow` |
| 409 | 陈旧版本、幂等键冲突、状态不允许或累计额度不足 |
| 413 | 请求体过大；Nginx 层的错误可能是 HTML |
| 429 | 入口限速触发；Nginx 层返回 |
| 501 | 功能尚未实现 |
| 503 | 业务接口遇到数据库操作故障；可附 `Retry-After` |

Django 的登录、后台、CSRF 和未捕获异常没有统一改为 JSON；前端不能假定所有非 200 响应都为 JSON。

## 分片上传（300MB 宣讲视频）

三个接口都要求登录态为学生账号，且响应统一走 `DomainError` 结构。单片固定 5MB，由服务端在 `chunk-start` 下发，前端不得自行决定。

| 方法与路径 | 用途 | 关键校验 |
|---|---|---|
| POST `/api/v1/uploads/chunk-start/` | 开一个分片任务（同名同大小会复用进行中的任务，实现断点续传） | material_type 必须在 `policies.STANDARD_MATERIAL_RULES` 内；文件名扩展名、file_size 上限按类别规则服务端判定；`total_chunks` 必须等于 `ceil(file_size/chunk_size)`；活动窗口、申报状态、额度、同时任务数 |
| POST `/api/v1/uploads/chunk-upload/` | 上传一片（multipart：`upload_id`、`chunk_index`、`chunk`） | 任务归属当前用户，否则 403；`chunk_index` 越界或单片超过 chunk_size 返回 400；同索引同长度分片已存在则直接 200（幂等，跳过重传） |
| POST `/api/v1/uploads/chunk-complete/` | 校验并合并全部分片 | 缺片、空片、总大小与声明值相差超过 ±1 片都会 400；第 1 片头 32 字节魔数校验与直传同一套规则 |

分片落在 `MEDIA_ROOT/tmp/<upload_id>/<index:06d>.part`，单片先写 `.tmp` 再 `os.replace`，中途断线不会留下半截 `.part`。合并成功后整个 tmp 目录删除，最终文件固定为：

```text
MEDIA_ROOT/<activity_id>/<student_number>/promotional_video/<uuid4().hex>.mp4
```

文件名只由 UUID 与扩展名组成，与用户上传的原始名无关；原始名保存为 `UploadSession.original_name`。`chunk-complete` 返回 `{"status": "uploaded", "final_path": "<相对 MEDIA_ROOT 的路径>"}`；数据库状态沿用 `UploadSession.Status.COMPLETE`（"complete"），API 层对外表述为 `uploaded`。

单片请求只承载 5MB，nginx/gunicorn 不再需要为一次 300MB 上传长时间占用 worker；换来的代价是同类别材料只允许一个进行中的分片任务。

分片任务的 `expires_at` 是 3 天，过期后由回收任务清理：

- `manage.py purge_stale_uploads`（支持 `--dry-run`、`--limit`、`--grace-hours`、`--json`）扫描 `status ∈ {reserved, uploading, completing, aborting}` 且 `expires_at` 已过的会话，删除 `media/tmp/<upload_id>/`、把 `reserved_bytes` 扣回、状态置 `aborted`，并写一条 `upload.purged` 审计（actor 为空，属系统行为）。
- `manage.py dispatch_outbox` 常驻循环默认每 `--purge-interval`（3600 秒）顺带执行一次，进程启动时先扫一次；`--no-purge` 或 `--purge-interval 0` 可关闭。
- 已 `complete` 的材料即使 `expires_at` 已过也不会被回收 —— 那是保留策略，不属于垃圾回收。

## 状态分离

文件上传状态：

```text
reserved → uploading → completing → complete
                    ↘ aborting → aborted
```

`reserved` 表示数据库额度预留，没有证明远程任务存在。当前本地预留、直传（`direct`）与浏览器分片（`chunked`）均已实现；`init/` 的对象存储预签名通道仍是 501。

分片任务在 `UploadSession` 上多记三个字段：`upload_mode`（direct/chunked）、`total_chunks`、`chunk_size_bytes`；开始分片时按文件大小预留额度，合并成功后才把预留转成已用，取消或删除时释放。

文件检查状态：`pending / valid / invalid / manual`，单独保存在 `FileAsset`。文件上传完成不等于格式通过，也不等于教师通过。

整份提交状态：`draft → submitted → approved / returned → 重新提交`。当前仅草稿保存行为已实现，正式提交与审核转换尚未开放。

后台任务状态：`pending → done / failed`。发布消息成功仍然是 `pending`，直到消费者完成并提交数据库结果才为 `done`。`failed` 需要排查原因；未实现的处理器不会标记成功。

## 身份与权限

学生 API 始终使用登录会话确定身份，只操作自己的数据。教师按活动和班级分配范围查询；学院管理员可跨班级查询。`is_staff` 是进入 Django 后台的权限标志，与业务角色是两个维度，应由受信任管理员配置。

当前用户模型已有姓名、班级和角色，学校认证/激活尚未接入。正式使用前需定义班级调动、审核分配变更和名单更新的规则；目前审核查询使用用户当前班级。

## 大小与额度口径

单文件硬上限：10,000,000,000 字节。单条 HTTP 业务请求上限：1MiB。单份草稿 JSON 上限：32KiB。文件分片默认参数：32MiB。当前账号同时活跃上传任务上限：2。

累计额度保存在 `StorageQuota`，首次预留时从活动配置复制。活动默认额度为 **12,884,901,888 字节（12 GiB）**，按目前规则可容纳 5 个 2000MB 打包件（10,485,760,000 字节）后仍余 2,399,141,888 字节给其他材料；单个 `.zip` 的 2000MB 上限高于类别 50MB，属于按扩展名特批。

活动额度之后调整不会自动回写已有额度账本，新建活动才使用新默认值；已存在的活动与账本不追溯。若需手工对齐某个活动，用下面的片段，约束是新额度不得小于已用与预留之和：

```python
from django.db.models import F
from apps.activities.models import Activity

Activity.objects.filter(quota_bytes_per_student=10_000_000_000).update(
    quota_bytes_per_student=12_884_901_888
)
```

同时注意 `StorageQuota.limit_bytes` 是首次预留时复制的冻结值，已有账本要单独评估后再调（存在 `limit_bytes >= used_bytes + reserved_bytes` 的数据库约束）。

## 安全拒绝与审计约定（阶段 2）

所有上传、访问、删除端点在 `@endpoint` 内层再套 `@audit_rejections("<action>")`。业务层抛出的 `DomainError` 或"记录不存在"会先落一条审计，再按原样返回错误响应，因此被拒绝的请求一定留痕。

审计字段固定为 `user(actor) / action / target / ip / reason / created_at`：

| 字段 | 说明 |
|---|---|
| actor | 发起请求的登录用户；匿名请求为空 |
| action | 现有点位：`upload.direct.rejected`、`upload.chunk_start.rejected`、`upload.chunk_upload.rejected`、`upload.chunk_complete.rejected`、`upload.file_access.rejected`、`upload.delete.rejected`、`submission.detail.rejected`、`submission.submit.rejected`、`access.role_denied` |
| target_type / target_id | 模型实例取 app_label.model 与主键；否则 `raw` + 请求里的 upload_id/activity_id |
| ip | 默认只取 `REMOTE_ADDR`；仅当 `TRUST_X_FORWARDED_FOR=true` 且逐跳 IP 校验通过时才采信代理头 |
| reason | 可读中文原因（越权、超限、魔数不符、ZipSlip 等），最长 300 字 |
| created_at | 落库时间 |

审计写入失败只降级为 `audit_write_failed` 日志，不影响本次响应。管理端 `/admin/audit/auditlog/` 按 action、target_type、时间筛选，支持搜学号/目标 ID/原因/IP，全程只读。
