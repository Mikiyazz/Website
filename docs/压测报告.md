## 3. 单 worker 排队判断（并发 P50 vs 串行 P50）

并发直传 P50 32 ms，串行 P50 34 ms，比值 **0.95x**。 比值接近 1，说明 50 并发下没有明显的 worker 排队。 登录单独统计：它走 PBKDF2 密码哈希，是 CPU 密集动作，50 个并发登录会把 CPU 打满，不能作为队列指标。
- P95/最大值的长尾主要来自 50 个并发登录同时做 PBKDF2 哈希把 CPU 打满，个别请求在 GIL 与磁盘 fsync 上排队；中位数比值接近 1，说明 Web worker 没有成为串行瓶颈。

## 4. 结论与优化方向

- 错误总数：0。
- 并发登录 P50 3679 ms、P95 9832 ms，主要由 PBKDF2 密码哈希决定；真实场景 600 人是错峰登录，不是 600 个请求同一秒到达。若登录风暴是已知场景，可换 Argon2 并调低迭代次数，或在网关层限流。
- 分片合并（chunk-complete）是单请求里最重的动作：要按序读回全部分片、计算 SHA-256、再落盘。若它的耗时明显高于单片上传，优化方向是把合并也丢给 Celery：chunk-complete 只做分片完整性校验并入队，worker 异步合并后回写 FileAsset，前端轮询状态；Web worker 立即释放。
- 若本轮使用 SQLite（开发/压测副本），写事务是串行的，结果只能作为功能链路压测；600 人真实规模必须在 docker compose + PostgreSQL 下用同一脚本复跑，行锁与连接池行为才有效。
