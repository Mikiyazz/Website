## 一、安全漏洞（SEC）

### [ ] SEC-01 · P0 · 跨用户存储型 XSS（`team_members_json|safe`）
- **代码位置**：
  - `mainbody/templates/submissions/apply.html` L634–L635
  - `mainbody/templates/submissions/outcomes.html` L437–L438
  - `mainbody/apps/submissions/views.py` L613、L634
- **现象与复现**：模板通过 `<script type="application/json">{{ team_members_json|safe }}</script>` 直接输出 `json.dumps` 结果，未转义 `</script>`。队长在 `team_members` 的 `real_name`/`class_name` 写入 `</script><script>...</script>` 并将团支书/管理员加为队员，受害者打开申报或成果页即执行任意 JS（已实测 `XSS_INJECTED = True`）。
- **修复方案**：
  1. 在视图上下文中直接传 Python 原生对象 `materials` / `team_members`（保留原变量或改用对象）；
  2. 模板全面改用 Django 内置 `{{ materials|json_script:"wizard-materials-json" }}` 和 `{{ team_members|json_script:"wizard-team-json" }}`（自动将 `<`、`>`、`&` 编码为 `\u003C` 等）；
  3. 检查并禁止在任意 `<script>` 区块里使用 `|safe` 输出用户可控 JSON。
- **验收标准**：构造含 `</script><script>alert(1)</script>` 的队员姓名渲染 `/submissions/apply/` 与 `/submissions/outcomes/`，响应 HTML 中不再出现裸 `</script><script>`，新增回归用例通过。

### [ ] SEC-02 · P0 · 改密接口传空/不传 `old_password` 绕过原密码校验
- **代码位置**：
  - `mainbody/apps/accounts/services.py` L195–L203
  - `mainbody/apps/accounts/views.py` L104–L118、L228–L260
- **现象与复现**：`if old_password is not None and str(old_password) != "":` 导致不传或传空字符串 `old_password` 时直接跳过原密码验证，返回 HTTP 200 并成功改密（已实测复现）。
- **修复方案**：
  1. 在 `change_password()` 中将 `old_password` 改为强制必填且非空（除非由管理员重置，走单独 `reset_password_to_default` 接口）；
  2. 为空时直接抛 `DomainError("请输入原密码。")`，并严格调用 `user.check_password(str(old_password))`；
  3. 同步核查现有 `tests/test_step1_security_and_rules.py` 等测试是否传了 `old_password`。
- **验收标准**：向 `/api/v1/accounts/change-password/` 与 `/accounts/change-password/` 发送缺失或空 `old_password` 请求返回 400 且密码不变；提供正确原密码返回 200/302。

### [ ] SEC-03 · P0 · 注册、改密与审核后 `next` 开放重定向（Open Redirect）
- **代码位置**：
  - `mainbody/apps/accounts/views.py` L224–L225、L259–L260、L1146–L1147
- **现象与复现**：未校验 `next` 参数，传入 `next=https://evil.example.com/phish` 或 `//evil.example.com` 会直接 302 跳转外站（已实测复现）。
- **修复方案**：封装统一工具函数 `_safe_next_url(request, raw_next, fallback="/")`，使用 `django.utils.http.url_has_allowed_host_and_scheme(url, allowed_hosts={request.get_host()}, require_https=request.is_secure())` 校验，不合法一律回退 `fallback`。
- **验收标准**：上述三个接口传入外链或协议相对 URL（`//evil.com`）均回退到站内默认页。

### [ ] SEC-04 · P1 · Excel 汇总导出公式注入（Formula Injection）
- **代码位置**：
  - `mainbody/apps/exports/services.py` L193–L207
- **现象与复现**：学生把项目名填成 `=HYPERLINK(...)` 或 `=CMD|...` 后，导出的 `.xlsx` 原样保留公式前缀未转义（已实测复现）。
- **修复方案**：导出写入单元格前，对所有字符串字段做安全转义——若去除前导空白后以 `=`、`+`、`-`、`@`、`\t`、`\r` 开头，前置单引号 `'`（或将单元格 `data_type` 设为纯文本并前置 `'`）。
- **验收标准**：项目名为 `=1+1`、`=HYPERLINK(...)` 时，导出的 Excel 单元格不作为公式求值。

### [ ] SEC-05 · P1 · 全院账号/管理员枚举 + 活动白名单泄露
- **代码位置**：
  - `mainbody/apps/accounts/views.py` L125–L165（`/api/students/lookup/`）
  - `mainbody/apps/activities/views.py` L39–L57（`/api/v1/activities/`）
- **现象与复现**：
  1. 任意学生调用 `/api/students/lookup/?student_number=...` 可遍历全院学生及管理员（如 `admin001`）的姓名、专业、班级与 `source`（是否已注册），且无频率限制；
  2. `GET /api/v1/activities/` 向普通学生返回了全量 `late_whitelist_student_numbers` 列表。
- **修复方案**：
  1. `student_lookup_view` 仅允许查询 8 位学号格式且排除 `is_superuser` / 非学生管理员账号，去掉 `source` 字段泄露，并对单用户加 Redis 限流（例如每分钟最多查询 30 次）；
  2. `activity_list` 对非管理员隐藏 `late_whitelist_student_numbers`，仅返回布尔值 `in_late_whitelist`。
- **验收标准**：学生查管理员账号返回 `exists: false`；学生请求 `/api/v1/activities/` 不含他人学号列表；高频枚举触发 429。

### [ ] SEC-06 · P2 · 密码策略不一致、`must_change_password` 未全局拦截、内联 PDF 缺沙箱头
- **代码位置**：
  - `mainbody/config/settings/base.py` L60–L65 vs `mainbody/apps/accounts/services.py` L65–L66、L207–L208
  - `mainbody/apps/uploads/views.py` L207–L231
- **现象与根因**：

  2. `file_access_view` 允许 `?inline=1` 在同源内联渲染用户上传的 PDF，未附带 `Content-Security-Policy: sandbox` 响应头。

  2. `file_access_view` 返回 inline 预览时追加 `Content-Security-Policy: sandbox` 和 `X-Content-Type-Options: nosniff`。
- **验收标准**：内联预览响应头包含 `Content-Security-Policy: sandbox`；密码规则前后端与配置保持一致。

## 二、高并发与 2000+ 人性能瓶颈（PERF）

### [ ] PERF-01 · P0 · 消除学生 GET 页面的 $O(N^2)$ 全表拉取 JSON 扫描
- **代码位置**：
  - `mainbody/apps/submissions/services.py` L179–L296（`map_activity_team_memberships_all`、`find_team_membership_activity_ids`、`redundant_member_draft_ids`）
  - `mainbody/apps/accounts/views.py` L275–L312
  - `mainbody/apps/submissions/views.py` L309–L420
- **实测数据**：2000 学生 + 1600 申报下，单个学生刷一次首页 `GET /` 耗时 **2030.6 ms**，等效生产 4 槽位吞吐仅 **1.79 req/s**，60 并发下 **36.7%（22/60）超过 20 秒超时**。
- **修复方案**：
  1. 新增规范化关系表 `SubmissionTeamMember(submission, activity, student_number, real_name, class_name)`，建立 `(student_number, activity)` 和 `(activity, student_number)` 联合索引，并编写数据迁移把历史 `draft_data["team_members"]` 同步入表；
  2. 在 `save_draft` / `submit_declaration` / `submit_for_review` / `delete_submission` 内原子同步更新 `SubmissionTeamMember`；
  3. 改写 `find_team_membership_activity_ids`、`find_team_membership_submissions`、`map_activity_team_memberships_all` 直接走索引查询，彻底消灭全表扫描 JSON；
  4. 为 `Submission` 新增布尔/索引字段（如 `is_empty_draft`、`declaration_type`、`category`）或直接用 SQL 过滤替代 `redundant_member_draft_ids` 的全表内存遍历。
- **验收标准**：2000 人数据集下，学生 `GET /` 单次响应 < 100 ms、SQL ≤ 10 条；60 并发零超时。

### [ ] PERF-02 · P0 · 严禁 GET 页面高频写库（消灭 PostgreSQL 5 行排他锁雪崩）
- **代码位置**：
  - `mainbody/apps/uploads/services.py` L43–L64（`ensure_standard_material_requirements`）
  - `mainbody/apps/accounts/views.py` L393、L424–L425、L874
  - `mainbody/apps/submissions/views.py` L408、L450–L452
- **实测数据**：学生每次 `GET /` 执行 **7 条写 SQL**（5 条 `MaterialRequirement` `update_or_create` + 1 条自动 `create_draft` + 1 条审计）；每次 `GET /submissions/apply/`、`/submissions/outcomes/`、`/admin-panel/` 执行 **5 条写 SQL**。2000 人同时访问将并发争抢同一个活动的同一批 5 行锁，直接撞穿 PostgreSQL `lock_timeout=3000ms` 全站 503/500。
- **修复方案**：
  1. `ensure_standard_material_requirements(activity)` 改为先只读查询该活动已有 `MaterialRequirement`（可配合短时 Redis 缓存），**仅在缺失标准 code 时才创建，且不再在 GET 路径执行无条件 `update_or_create`**；规则变更迁移改用管理命令或保存活动时同步；
  2. 移除学生 `GET /` 首页自动调用 `create_draft()` 的写库副作用（仅在进入 `/submissions/apply/` 或首次点击保存/上传时按需创建草稿）。
- **验收标准**：学生访问 `GET /`、管理员访问 `GET /admin-panel/` 写 SQL 数量严格为 **0**。

### [ ] PERF-03 · P0 · 拆分大文件合并与校验出数据库长事务（防撞穿 15 秒断连与数据丢失）
- **代码位置**：
  - `mainbody/apps/uploads/chunks.py` L447–L631（`complete_chunked_upload`）
  - `mainbody/apps/uploads/services.py` L329–L538（`direct_upload`）
  - `mainbody/config/settings/base.py` L46（`idle_in_transaction_session_timeout=15000`）
- **根因**：在 `@transaction.atomic` + `select_for_update()` 锁内同步合并 300MB–2GB 文件、计算 SHA-256 及跑最长 25s 的 `ffprobe`，超过 15 秒即被 PostgreSQL 强制断开连接返回 500 并残留孤儿大文件；同时 `shutil.rmtree` / `_remove_physical_file` 在事务提交前删掉旧文件，一旦回滚造成永久丢数据。
- **修复方案**：
  1. **三段式状态机**：短事务 1（`select_for_update` 校验权限/活动窗口/状态，把 `status` 置为 `COMPLETING` 后立即提交释放行锁） → **事务外**执行合并、SHA-256 与 `validate_stored_file_content`（大文件如 > 50MB 建议更进一步交由 Celery 异步合并） → 短事务 2（锁行结算配额、置 `COMPLETE`、建 `FileAsset`、标记旧记录 `ABORTED`）；
  2. 所有删除旧物理文件与 `shutil.rmtree(chunk_tmp_dir)` 统一放进 `transaction.on_commit(...)`；事务外异常时负责清理刚写出的 `final_path` 并将状态回退至 `UPLOADING`；
  3. `direct_upload` 同样先在事务外流式落盘到临时文件并完成内容校验，最后再开短事务结算配额与落库。
- **验收标准**：大文件直传/合并期间数据库连接占用时间 < 100 ms，不会触发 `idle_in_transaction_session_timeout`；任意异常回滚不丢失旧文件、不残留临时孤儿文件。

### [ ] PERF-04 · P1 · 消除管理面板 2.95 MB 无分页 HTML 渲染与团支书跨班全表扫描

### [ ] PERF-05 · P1 · 消除审核列表 107 次 N+1 查询与审核事务内全表扫描
- **代码位置**：
  - `mainbody/apps/reviews/views.py` L49–L61（`serialize_submission_for_review`）

### [ ] PERF-06 · P1 · 2000MB `.zip` 接入分片上传 + 后台批量初始化改异步/分批

## 三、部署与容器架构隐患（OPS）

### [ ] OPS-01 · P0 · 修复 Gunicorn 4 槽位过小 + 大文件下载改走 Nginx `X-Accel-Redirect`
- **代码位置**：
  - `mainbody/deploy/gunicorn.conf.py` L3–L11
  - `mainbody/compose.yaml` L61–L96
  - `mainbody/apps/uploads/views.py` L220–L230
  - `mainbody/apps/exports/views.py` L187
- **实测数据**：4 个慢上传占满 4 槽位后，`/health/live/` 直接超过 4 秒超时（4022 ms ReadTimeout），全站假死。
- **修复方案**：
  1. `nginx` 容器只读挂载 `media_data:/app/media:ro`，配置 `location /internal-media/ { internal; alias /app/media/; }`；
  2. 生产模式下，`file_access_view` 与 `download_export` 鉴权通过后返回空响应 + `X-Accel-Redirect: /internal-media/<relative_path>` 与 `Content-Disposition`，把大视频/大 ZIP 下载彻底卸载给 Nginx 异步处理；
  3. 上调服务器与容器规格（面向 2000 人建议 4C8G 起步）：`web` 容器 `cpus: 2.0–4.0`、`mem_limit: 2g`，`gunicorn.conf.py` 调至 `workers = 4`、`threads = 4`（16 槽位，启用 `preload_app = True` 省内存），`db` 调至 `max_connections=120`、`shared_buffers=256MB`、`mem_limit: 1536m`。
- **验收标准**：4 个并发慢上传或大文件下载期间，`/health/live/` 响应 < 50 ms，普通页面正常打开。

### [ ] OPS-02 · P0 · 修复 Nginx 校园网 NAT 限流误杀（`6r/m` 集体 429）
- **代码位置**：
  - `mainbody/deploy/nginx.conf` L3–L4、L26–L41
- **根因**：校园网宿舍楼出口 NAT 或学校前置反代下，数百上千学生共享极少数 IP，`login_rate=6r/m burst=10` 会导致第 17 个同楼登录学生直接 429。
- **修复方案**：
  1. 若前置有学校 Nginx/负载均衡，配置 `set_real_ip_from` 与 `real_ip_header X-Forwarded-For; real_ip_recursive on;`；
  2. Nginx 层 IP 限流改为校园网友好阈值（如登录 `60r/m burst=120`，API `120r/s burst=300`），仅防极端 DDoS；
  3. 真正的防爆破限流在 Django 登录视图用 Redis 按「学号（`username`）维度」做失败次数锁定（例如单学号连续输错 5 次锁定 10 分钟），既防撞库又不误杀同宿舍楼正常学生。
- **验收标准**：同 IP 下 100 名不同学号学生 1 分钟内并发登录 0 个 429；单学号连续错密 5 次被拦截。

### [ ] OPS-03 · P0 · 修复 `production.py` 与 `nginx.conf` HTTP/HTTPS 无限 301 死循环
- **代码位置**：
  - `mainbody/config/settings/production.py` L15–L20
  - `mainbody/deploy/nginx.conf` L6–L19
- **根因**：`production.py` 强制 `SECURE_SSL_REDIRECT = True` 并要求 `X-Forwarded-Proto: https`，但 `nginx.conf` 仅监听 80 且固定传递 `X-Forwarded-Proto $scheme`（恒为 `http`），按现有编排切生产配置立刻死循环。
- **修复方案**：提供清晰的两种部署模板——① 独立 TLS 模板（Nginx 监听 443 + 80 跳 443，挂载证书）；② 前置校园网 HTTPS 网关模板（明确说明反代透传并覆盖 `X-Forwarded-Proto`），并在 `compose.yaml` 与 `docs/运行与可靠性说明.md` 对齐。
- **验收标准**：用生产配置通过容器启动后，首页与登录页无 301 循环，安全 Cookie 与 HSTS 正常生效。

### [ ] FUNC-01 · P0 · 修复中途取消分片上传导致用户 72 小时无法再传新视频
